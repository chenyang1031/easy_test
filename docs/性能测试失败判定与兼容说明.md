# 性能测试失败判定 — 新旧逻辑与兼容

## 1. 旧逻辑（阶段1）

- 无 `extra_config.assertions` 时：**仅依赖 HTTP 层失败**（Locust 对非成功响应的统计；阶段2 起对 `catch_response=True` 显式标记 HTTP ≥ 400 为失败）。
- 未区分超时、连接错误、业务失败等维度。

## 2. 新逻辑（阶段2）

- **HTTP**：状态码 ≥ 400 记为请求失败，并计入 `error_classification.http_status_error`（在可分类前提下）。
- **超时 / 连接错误**：捕获 `requests` 异常，记失败并分别计入 `timeout` / `connection_error`。
- **业务断言**：若配置了 `assertions`，在响应体解析为 JSON 后按 jsonpath 规则校验；失败记为 Locust failure，并计入 `assertion_failure`。

## 3. 优先级与切换规则

1. 若 **`assertions` 未配置或为空**：不进行 JSON 业务校验，**仅 HTTP/传输层**规则生效（与旧行为一致，仅统计维度更细）。
2. 若 **配置了 `assertions`**：HTTP 成功（通常 2xx）后才执行断言；断言失败**单独计数**到 `assertion_failure`，与 HTTP 错误区分。

## 4. 兼容存量任务

- 未配置 `assertions`、`stages`、`think_time_ms`、`csv_file` 的任务行为与阶段1一致（仍可用新字段默认值 0 / `{}` 展示报告）。
