## 2. 目标与原则

### 2.1 业务目标

1. **可见**：场景编排的执行与资产在平台总览中可统计、可追踪。  
2. **可归档**：场景执行结果可进入统一「测试报告」体系，便于留痕与对比。  
3. **可演进**：单接口测试线与 AI 草稿规则清晰；性能测试按阶段补齐，避免一次性大改。  
4. **可扩展**：数据模型与 API 预留扩展字段，避免重复造轮子。

### 2.2 技术原则

- **项目口径**：涉及业务 `Project` 的归属时，优先 **`Environment.project`**；`ApiProject.platform_project` 仅作展示增强。  
- **少侵入**：优先扩展现有 `TestReport`、`PerformanceTestTask.extra_config`、`ParameterConfig`。  
- **性能与分布式解耦**：单机压测（Locust + Celery）与分布式发压分阶段，不混在同一里程碑的必交付项。

### 2.3 名词

| 名词 | 含义 |
|------|------|
| 场景执行 | `TestSceneExecution` 一次运行记录 |
| 传统测试运行 | `TestRun` + `TestResult`（HttpRunner 单接口用例） |
| 阶段1 压测 | 当前已实现：单接口、单机 Locust、基础时序与摘要报告 |

## 4. 分模块细粒度方案

### 4.1 模块 A：仪表盘接入【测试场景编排】

#### 4.1.1 现状与差距

- 仪表盘统计 `Project` / `TestCase` / `TestSuite` / `TestRun` / `TestReport` 时间序列，**不含** `TestScene` / `TestSceneExecution`。

#### 4.1.2 任务分解（可勾选）

| 任务 ID | 描述 | 产出物 | 估 PD |
|---------|------|--------|-------|
| A-1 | `dashboard` 视图增加计数：`TestScene`（`is_deleted=False`）、`TestSceneExecution` 总数 | 视图 context | 0.5 |
| A-2 | 执行状态分布：`running/success/failed` 聚合（注意 `running` 异常滞留可后续治理） | context | 0.5 |
| A-3 | `generate_time_series_data` 扩展：`TestScene` 按 `created_at`、`TestSceneExecution` 按 `created_at` 或 `finished_at`（二选一写死并文档化） | 函数扩展 + 单测 | 1～1.5 |
| A-4 | 最近场景执行列表：N 条（如 5），字段：场景名、环境名、状态、耗时、`created_at` | queryset + 模板 | 1～2 |
| A-5 | `dashboard.html`：卡片 + 图例 + Chart 数据集接线 | 模板/静态资源 | 1～2 |
| A-6 | 可选：按 `project_id` GET 参数筛选（若全局仪表盘无项目上下文则降级为不做） | 参数 + 过滤 | 0.5～1 |
| A-7 | 权限与性能：列表 `limit`；说明大量执行时的索引（已有 `scene+created_at` 等） | 注释/文档 | 0.5 |

**模块 A 合计**：约 **5～10 PD**。

#### 4.1.3 验收标准

- 有场景数据时卡片与曲线正确；无数据时不报错。  
- 最近执行与详情页入口（链接到现有场景编排 URL）可点击。

#### 4.1.4 可扩展（后续 backlog）

| 扩展项 | 说明 |
|--------|------|
| A-X1 | 「混合活动流」：`TestRun` 与 `TestSceneExecution` 按时间合并（需统一展示模型） |
| A-X2 | 按业务 `Project` 过滤场景统计（需厘清 `ApiProject` 与 `Project` 多对一关系） |
| A-X3 | 与通知/Webhook 联动：场景连续失败告警 |

### 4.2 模块 B：【测试报告】与【测试场景编排】结合

#### 4.2.1 现状与差距

- `TestReport` 关联 `test_run` / `test_suite_run` / `test_results`，**无** `TestSceneExecution`。  
- 场景执行已含 `node_results`、`summary`、耗时、环境等，**具备报告素材**。

#### 4.2.2 任务分解

| 任务 ID | 描述 | 产出物 | 估 PD |
|---------|------|--------|-------|
| B-1 | 迁移：`TestReport.scene_execution` FK（`SET_NULL`）、`report_type` 增加 `scene_execution` | migration | 0.5～1 |
| B-2 | `TestReportForm` / Admin / Serializer 可选字段 | 表单与后台 | 0.5～1 |
| B-3 | 生成服务函数：`build_scene_execution_report_content(execution) -> {html, json}` | 独立模块防视图臃肿 | 2～4 |
| B-4 | JSON 结构规范：顶层含 `scene`、`environment`、`execution`、`nodes[]`（与 `node_results` 对齐） | 文档 + 代码 | 1～2 |
| B-5 | HTML 模板：节点折叠块、大 body 截断（与 TestRun 报告策略一致） | 模板字符串或 Django template | 2～3 |
| B-6 | `project_id` 来源：`execution.environment.project_id`（强制校验存在） | 校验逻辑 | 0.5 |
| B-7 | 视图：`generate_scene_execution_report(request, execution_id)` + 权限（同项目或 staff） | URL + view | 1～2 |
| B-8 | 可选 REST：`POST /api/.../scene-executions/{id}/export-report/` 返回 `report_id` | DRF | 1～2 |
| B-9 | `get_summary()` 扩展：识别 `scene_execution` 类型 JSON | 方法扩展 | 0.5～1 |
| B-10 | 报告列表页：按类型筛选、显示关联场景名 | 模板 | 0.5～1 |

**模块 B 合计**：约 **8～16 PD**（含可选 API）。

#### 4.2.3 验收标准

- 从一次已完成（或失败）的执行生成报告，`content` 可打开，摘要字段正确。  
- 删除执行不级联误删报告（FK `SET_NULL` 行为符合预期）。

#### 4.2.4 可扩展

| 扩展项 | 说明 |
|--------|------|
| B-X1 | 报告对比：两次 `TestSceneExecution` diff（节点级） |
| B-X2 | PDF 导出（复用 HTML→PDF 服务或库） |
| B-X3 | 报告水印、只读分享链接（`is_public` 已有） |

## 6. 风险与开发注意事项

### 6.1 数据与性能

- **大字段**：`TestReport.content`、`node_results` 写入需截断策略一致。  
- **仪表盘**：时间序列查询注意时间窗口与索引；高并发执行表增长后考虑归档策略。

### 6.2 权限与安全

- 场景报告、压测任务：与 **项目成员** 或 **创建人** 策略对齐，避免 ID 遍历。  
- AI 与外部 HTTP：`ParameterConfig` 密钥不入库日志明文。

### 6.3 性能压测特有风险

- **施压机瓶颈**：单机 CPU/句柄打满导致指标失真 → 文档说明 + E-5 监控。  
- **Celery 长任务**：`time_limit`、`soft_time_limit` 与 Locust `run_time` 对齐。  
- **gevent + Django**：`performance_locust` 已注意 DB 连接回收，扩展时保持模式。

### 6.4 迁移与兼容

- `TestReport` 新增字段一律可空；旧报告类型不变。  
- 性能结果表加列需考虑历史行默认值与前端兼容。
